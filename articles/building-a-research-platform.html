Building a Live Research Platform

How a static cosmology site became an interactive research hub with real-time data, AI chat, and human review tools

TECHNICAL INFRASTRUCTURE WEB 2026

1. From Static to Dynamic

The BigBounce website started the way most research sites do: a handful of HTML files summarizing a paper. An index page with key results. A figures gallery. A glossary. The kind of thing you put together in a weekend to make your work accessible beyond the PDF.

Then the research grew. What began as a single paper became a 24-branch research program with 424,000+ MCMC samples, 14 structural barriers, and multiple falsifiable predictions. The static site couldn't keep up. We needed the site to do things that static HTML cannot do on its own:

  • Persist visitor feedback and analytics without third-party trackers
  • Let visitors ask questions about the research and get real answers
  • Track the status of running MCMC chains and compute pipelines
  • Manage a human review pipeline for DESI spectral anomalies
  • Provide an admin dashboard for monitoring everything

The question was: how do you add all of this without turning a clean, fast, content-first website into a bloated single-page application?

The answer turned out to be simpler than expected.

2. The Stack

The BigBounce platform runs on three layers:

Frontend

Vanilla HTML/CSS/JS

No React. No Vue. No Svelte. No build step. Plain HTML files with a shared stylesheet and a single nav.js file that injects navigation across all 26 pages.

Backend

Convex

A reactive backend-as-a-service that handles persistence, real-time subscriptions, and server-side mutations. Accessed directly from the browser via the Convex JS client — no API server needed.

Edge

Vercel Edge Functions

Handles the AI chat proxy (routing to Claude Sonnet via OpenRouter) and any server-side logic that can't run in the browser. Deployed alongside the static files.

Why this combination works:

Zero Build Step

There is no npm run build. There is no webpack, no Vite, no bundler. You edit an HTML file, push to main, and Netlify deploys it. The entire site is the source code. This has a surprising secondary benefit: any AI agent can edit the site directly. There's no compilation layer between the code and the output, which makes AI-assisted development dramatically simpler.

The static frontend talks to Convex for persistence and to Vercel Edge Functions for AI chat. That's the entire architecture. No ORM. No database migrations. No Docker containers. No Kubernetes.

3. What We Built

Here's a walkthrough of the major features, roughly in the order they were added.

Convex Data Layer

Convex provides the persistence layer for everything dynamic on the site. The tables include:

Table Purpose Records
reviews Human review labels for DESI spectral anomalies 70+
chatMessages Astro chatbot conversation logs and feedback Growing
analytics Page view tracking (path, referrer, session hash) Growing
activityFeed Research activity timeline entries 50+
mcmcStatus Running chain status and convergence metrics Per-chain
spectralResults DESI spectral anomaly classification results 195,000+

Every mutation is called directly from the browser using the Convex HTTP client — a single <script> tag loaded from a CDN. No backend server, no API routes, no CORS configuration.

Admin Dashboard

A protected admin page provides a unified view of the platform:

  • Chat session browser: View all Astro chatbot conversations, filter by date, see full message threads
  • Analytics overview: Page view counts, top pages, referrer breakdown, visitor timelines
  • Activity manager: Add, edit, and reorder research timeline entries
  • Review pipeline status: Track progress on human verification of AI-classified anomalies

Astro: The Research Chatbot

Astro is an AI chatbot embedded on every page of the site. It uses Claude Sonnet (via OpenRouter) to answer visitor questions about the BigBounce research. The implementation:

  • Frontend widget loaded via chat-widget.js
  • Messages streamed via SSE (Server-Sent Events) from a Vercel Edge Function
  • Conversations persisted to Convex with page context (which page the user was on)
  • System prompt grounded in the actual research content
  • Full conversation history maintained per session

Astro knows about the 14 barriers, the surviving predictions, the MCMC results, and the ECH framework. It doesn't hallucinate physics because its system prompt anchors it to the specific claims and numbers from the research.

Human Review Pipeline

The DESI spectral anomaly pipeline classified 195,000+ objects using AI. But AI classification needs human verification. We built a review interface directly into the site:

  1. 70 representative anomalies selected for human review
  2. Each anomaly shows the AI classification, confidence score, and spectral data
  3. Human reviewer confirms, overrides, or flags for further analysis
  4. Results stored in Convex with both AI and human labels
  5. Agreement rate tracked to validate the AI pipeline

Shared Navigation

One of the earliest infrastructure decisions was centralizing navigation in a single nav.js file. With 26 pages across root, articles, and research subdirectories, maintaining nav HTML in every file was unsustainable. The nav script:

  • Detects its depth from the URL (root, articles/, research/) and adjusts link prefixes
  • Highlights the active page
  • Injects mobile hamburger menu
  • Includes site search (Cmd+K / Ctrl+K)
  • Handles dark mode toggle

Additional Features

  • Dark mode: Full dark theme with CSS custom properties, respects system preference
  • Site search: Cmd+K overlay that searches across all pages
  • Print styles: Clean print output for any page
  • Page view analytics: Privacy-respecting, first-party, session-hashed — no cookies
  • Visitor feedback: Thumbs up/down widget on every article and page

4. Why Not a Framework?

This is the question everyone asks. Why not React? Why not Next.js? Why not Astro (the framework, not our chatbot)? It's a fair question, and the honest answer has tradeoffs on both sides.

Why plain HTML works for this project

  • No build step: Edit a file, push, deployed. No compilation, no bundling, no "it works on my machine."
  • AI-agent-friendly: Any AI coding assistant can read, understand, and edit plain HTML. No framework abstractions to navigate, no component trees to understand, no state management to reason about.
  • Instant page loads: No JavaScript bundle to parse before content appears. The HTML is the content.
  • Content-first: This is a research site. The content is the product. Frameworks optimize for interactivity; we optimize for reading.
  • Longevity: HTML from 1999 still renders perfectly. React components from 2019 may not compile without dependency updates. For a research archive that should remain accessible for decades, plain HTML is the safest bet.

The real downsides

We should be honest about what we give up:

  • No component reuse: Common patterns (cards, stat blocks, equation displays) are copy-pasted, not abstracted. Changes to a pattern require updating every instance.
  • No TypeScript on the frontend: Type safety only exists in the Convex backend. Frontend JS is untyped.
  • Nav duplication was painful — until we solved it with nav.js. But other shared elements (footer, feedback widget, analytics snippet) are still duplicated.
  • Interactive features are harder: The data explorer page, with its sortable tables and equation calculators, would be cleaner as React components. We made it work with vanilla JS, but it took more code than it should have.

When would we switch?

If the interactive surface keeps growing — if we add more dashboard features, more real-time visualizations, more complex data tools — the balance tips toward a framework. The threshold is roughly: when more than half the development time is spent on interactivity rather than content, it's time to consider a migration. We're not there yet. The site is still primarily a reading experience with dynamic features layered on top.

5. For Other Researchers

If you are a researcher thinking about sharing your work online, here is the simplest path I can recommend based on what we learned:

The Minimal Research Platform Stack

  1. Start with HTML. Write your research as web pages. Use a single style.css. Include MathJax for equations. This gets you 80% of the way.
  2. Add Convex when you need persistence. The moment you want feedback, analytics, or any form of data storage, add the Convex browser bundle (one script tag) and write your mutations. No server to manage.
  3. Use Vercel or Netlify for hosting. Push to GitHub, auto-deploy. Free tier is more than enough for a research site.
  4. Add AI chat if your research is complex. A chatbot grounded in your actual findings can answer visitor questions better than a FAQ page. Use an edge function to proxy the LLM API.
  5. Centralize your nav early. If you have more than five pages, write a nav.js that injects navigation. You'll thank yourself later.

You do not need React to build something useful. You do not need a design system, a component library, or a state management solution. You need HTML, a stylesheet, and the willingness to ship something imperfect and iterate.

The BigBounce site has 26 pages, an AI chatbot, a review pipeline, real-time analytics, an admin dashboard, and a full data explorer — and it was built by one person using plain HTML and a handful of backend services. If that's not proof that you can do this too, I don't know what is.

The best research platform is the one that exists. Don't let tooling decisions delay sharing your work. Start with HTML. Add complexity only when the research demands it.
