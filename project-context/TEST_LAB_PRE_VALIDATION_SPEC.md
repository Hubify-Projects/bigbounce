## 0. The premise

Before the BigBounce migration runs against real research data, we build a **tiny synthetic-data test lab** to validate the entire migration + bootstrap + first-research-cycle flow against fake data. If the test lab succeeds end-to-end, we have high confidence the real BigBounce migration will succeed. If it fails, we fix the failures cheaply (no real data lost).

This is the **dry run**. Cost: ~1 day of work. Benefit: prevents catastrophic data loss on the real lab.

---

## 1. Why a test lab and not just unit tests

Unit tests cover individual functions. The test lab covers the **integration surface** — the place where the import script + the orchestrator bootstrap + the first end-to-end research cycle all touch each other. Bugs in that surface are the kind that destroy data.

Specific risks the test lab catches:
- Import script silently truncates a directory (e.g., `pipelines/p3_anomaly_engine/` is too deeply nested)
- Convex schema migration fails on a field type the new lab uses but the platform doesn't expect
- Fly.io machine boots but can't reach the Convex deployment due to env var typo
- RunPod compute integration hangs at "waiting for credits check" because the credits-API call is rate-limited
- Backup pipeline fires nightly but writes to the wrong B2 bucket because of a path-prefix bug
- Cross-lab Sovereignty Rule has a hole somewhere (e.g., `experiment dispatch` from Lab B against Lab A's experiment ID accidentally succeeds)

None of these are catchable in unit tests because they involve multi-vendor integration. The test lab is the only way to catch them before production.

## 2. The test lab content (synthetic)

### 2.1 Lab metadata

```yaml
name: test-lab-alpha
slug: test-alpha
mission: |
  Synthetic test lab for pre-validating the Hubify Labs migration + bootstrap pipeline.
  All data is fake. No real research. This lab exists to be migrated and torn down.
visibility: private
created: 2026-04-XX (whichever day the build happens)
owner: houston@hubify.com
```

### 2.2 Synthetic projects (3)

| Project | Goal | Pipeline | Experiments |
|---|---|---|---|
| `p1-fake-mcmc` | "Recover the synthetic injected H₀ value from a fake MCMC chain" | `fake-mcmc-pipeline` (3 steps) | 5 fake MCMC runs |
| `p2-fake-anomaly` | "Find the 100 injected anomalies in the synthetic catalog" | `fake-anomaly-detection` (4 steps) | 8 fake anomaly batches |
| `p3-fake-paper` | "Compile the test paper end-to-end through the publish-ready loop" | `fake-paper-compilation` (5 steps mirroring the publishing-lead flow) | 3 fake paper compile runs |

### 2.3 Synthetic data

| Dataset | Size | Format | Generated by |
|---|---|---|---|
| `fake_mcmc_chain.csv` | ~10 MB · 50K rows · 8 columns | CSV | Numpy `random.normal` with H₀ injected at 67.5 ± 0.5 |
| `fake_anomaly_catalog.csv` | ~5 MB · 1K rows · 12 columns | CSV | Mostly random, 100 rows tagged as "anomaly=true" |
| `fake_paper.tex` | ~50 KB | LaTeX (revtex4-2) | Hand-written 4-page test paper that compiles cleanly |
| `fake_figures.png` (5) | ~500 KB total | PNG | matplotlib placeholders |

**Total:** ~16 MB of fake data. Negligible storage cost.

### 2.4 Synthetic agents

The test lab uses the standard agent roster (per PRD §3) but with **no real cross-model peer review** (mock the GPT/Gemini/Grok/Perplexity calls to return canned responses). Reasons:
- We're testing the platform mechanics, not the actual peer review quality
- Skipping real API calls saves ~$50 in test costs
- Mock responses can be deterministic, which makes test runs reproducible

### 2.5 Synthetic compute

| Compute | Real or fake? | Why |
|---|---|---|
| RunPod credits check | REAL | We need to verify the API integration works |
| RunPod pod dispatch | FAKE | Use a stub pod (return "pod_id=test_001") to avoid actual GPU spend |
| Fly.io orchestrator machine | REAL | We need to verify the machine boots and can reach Convex |
| Convex deployment | REAL | The whole platform runs on it |
| Backblaze B2 backup | REAL (separate bucket: `b2://test-cold/`) | We need to verify backups actually write |
| Anthropic API for chat | REAL but capped at $5 budget | Need real chat to test the orchestrator's decision-making |

**Estimated test-lab compute cost:** ~$8 (Anthropic chat $5 + Fly machine $2 + Convex usage $1).

## 3. The validation script — what gets exercised

The test lab build executes every step of the migration plan against fake data:

### Step 0 — Pre-migration backup
- [ ] Run `pre-migration-backup.sh` against the test lab seed directory
- [ ] Verify the backup tarball lands in `b2://test-cold/test-lab-pre/`
- [ ] Verify the tarball is restorable

### Step 1 — Repo creation
- [ ] Create `Hubify-Labs/test-lab-alpha` repo on GitHub
- [ ] Verify the platform's "create new lab" flow scaffolds the standard directory structure
- [ ] Verify `lab.yaml` has the expected fields

### Step 2 — File system import
- [ ] Run the import script with the synthetic seed data
- [ ] Verify all 3 projects + 16 experiments + 1 fake paper land in the right tier per `map.md`
- [ ] Verify Z1 source goes to T1+T2, Z2 state goes to T4, Z3 compute (fake) goes to T7 stub
- [ ] Verify nothing was silently truncated (compare directory file counts before/after)

### Step 3 — Orchestrator bootstrap
- [ ] Provision Fly.io test machine `orchestrator-test-alpha.fly.dev`
- [ ] Verify it boots, registers with Convex, picks up the lab slug
- [ ] Verify the orchestrator can read its lab metadata
- [ ] Verify it spawns the standard 21 agents (per §3 PRD)

### Step 4 — Site deploy
- [ ] Trigger the lab's site deploy via the platform
- [ ] Verify Vercel deploys `https://test-alpha.hubify.app` successfully
- [ ] Verify the site renders fake content (3 fake project cards, 1 fake paper, fake anomaly stats)

### Step 5 — Compute handoff
- [ ] Verify the orchestrator's RunPod credentials are accessible from Convex env vars
- [ ] Verify the credits API call returns valid JSON (mock the response)
- [ ] Verify the dispatch flow correctly returns "test pod ID" for fake dispatches

### Step 6 — First end-to-end research cycle
- [ ] Houston (or test script) starts a chat: "let me look at the fake MCMC results"
- [ ] Verify the chat correctly references the fake_mcmc_chain.csv via `data://chains/`
- [ ] Verify the orchestrator routes to cosmology-worker
- [ ] Verify cosmology-worker generates a fake "H₀ recovered = 67.48 ± 0.52" result
- [ ] Verify the result is committed to the lab's wiki via wiki-worker
- [ ] Verify activity feed shows all 5+ events from the chain
- [ ] Verify the publish-ready loop runs against `fake_paper.tex` and reaches Round 5 successfully

### Step 7 — DNS cutover
- [ ] Skip — test lab uses `test-alpha.hubify.app` directly, no cutover needed

### Step 8 — Post-migration verification
- [ ] All 3 projects show up in the Director view
- [ ] All 16 experiments are queryable from the experiments table
- [ ] The fake paper shows up at 100% readiness on the Papers view
- [ ] The Lab Sovereignty Rule blocks a write attempt from a different lab token (positive test)

### Step 9 — Backup
- [ ] Trigger an immediate backup of the test lab → B2
- [ ] Verify the backup completes
- [ ] Verify the backup tarball contains the expected file count

---

## 4. Pass/fail criteria

The test lab passes pre-validation when:

1. **All 9 steps above complete with no errors**
2. **All checkboxes in the validation script are `[x]`**
3. **The Lab Sovereignty Rule blocks the cross-lab write attempt** (negative test passes)
4. **The publish-ready loop reaches Round 5 successfully** on the fake paper
5. **Total test-lab cost is under $15** (sanity check that nothing ran away)

If any of these fail, the migration to BigBounce is **BLOCKED** until the failure is fixed and the test lab re-runs to a clean pass.

---

## 5. Tear-down (after pass)

Once the test lab has passed:

1. Tag the test lab as "validated" in its `lab.yaml`
2. Backup it one more time to `b2://test-cold/test-lab-validated/`
3. Tear down the Fly.io machine (no point keeping it running)
4. Keep the GitHub repo and the Convex tables for posterity (cheap, useful for regression testing)
5. Mark `BUILD_READINESS_CHECKLIST.md` H8 as `[x]` with the validation date

The test lab can be re-resurrected at any time by running `hubify lab restart test-alpha`.

---

## 6. What happens if the test lab fails

If the validation script fails at any step:

1. **STOP.** Do not run the BigBounce migration. The platform isn't ready.
2. Diagnose the failure (logs from Fly machine + Convex + import script)
3. Fix the bug in the platform (whichever component is broken)
4. Re-run the validation script from the failing step
5. Iterate until the test lab passes

This is **non-negotiable**. Running the BigBounce migration on a platform that fails its own dry run would be catastrophic.
