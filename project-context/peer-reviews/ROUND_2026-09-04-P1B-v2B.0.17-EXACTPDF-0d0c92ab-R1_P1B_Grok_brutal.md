**Referee Report for P1B (JORS-SOFTWARE)**

**P1B-E1** (Abstract, p. 1; §6 p. 3–4)  
The abstract states the verifier “detected all 12 runs (100%) drawn from four shortcut classes … with a 0% false-positive rate on 3 honest runs”. The body (Table 2) confirms exactly these numbers, but only for the authors’ own spin-0 MASTER implementation. The abstract does not qualify that the 100 % figure was obtained on a non-NaMaster code base.  
**Required fix:** Add the explicit qualifier “on the authors’ own spin-0 implementation, not NaMaster” to the abstract sentence.

**P1B-E2** (Abstract, p. 1; §10 p. 6)  
Abstract claims the method supplies “a cheap consistency check against a declared contract under a non-adversarial-analyst threat model”. Section 10 explicitly states the tested claim “cannot in principle catch metadata forgery (an adversary who runs the shortcut and then writes the honest trace by hand)”. The abstract therefore over-states the security guarantee.  
**Required fix:** Replace “non-adversarial-analyst threat model” with the precise limitation already written in §10.

**P1B-E3** (§1 p. 1; §6 p. 3)  
The introduction presents namaster-proof as a verification layer for NaMaster, yet every quantitative result (§6, Table 2, wall-time numbers) was obtained with the repository’s own PyMaster spin-0 code. No NaMaster run appears in the sealed test. This violates the standalone-reader requirement: the central performance claim cannot be evaluated from the paper alone.  
**Required fix:** Either rerun the blind protocol on actual NaMaster or move all numerical claims to an explicitly labelled “demonstration on a surrogate estimator” subsection.

**P1B-M1** (§6 p. 4)  
The protocol description states “the seal was independently verified” but supplies only the first eight characters of the assignment digest (“0f4ca4ba…”) and no external timestamp or third-party witness. Under the threat model the authors themselves declare, this is insufficient to close the S5 forgery vector.  
**Required fix:** Provide either a cryptographic timestamp or a reproducible external anchor; otherwise remove the word “independently”.

**P1B-M2** (entire manuscript)  
JORS software papers are expected to be concise descriptions of reusable tools. The present work is an 8-page specialized verification study whose primary artefact (the blind-test harness) is exercised only on the authors’ own estimator. The contribution is therefore narrower than the venue’s typical accepted paper; recommended maximum length for this scope is 4–5 pages.

**P1B-N1** (p. 1 header)  
“September 4, 2026 — manuscript revision v2B.0.17” is internal versioning language that should not appear in a submitted manuscript.

**P1B-N2** (§7 p. 5)  
The 41 automated tests are cited as evidence of quality, yet two of them are explicitly skipped in a standalone install because they replay against production helper modules that reside outside the package. This reduces the effective test coverage below the advertised number; the discrepancy should be stated quantitatively.

**Summary recommendation**  
**MAJOR REVISIONS**

The manuscript presents a narrowly scoped verification layer whose headline empirical claim (100 % shortcut detection) rests entirely on a surrogate spin-0 code base rather than the advertised NaMaster target. The abstract further over-states the security properties that the authors themselves qualify in §10. These two mismatches between claim and evidence are essential for a software metapaper whose central selling point is reproducible, auditable computation. Until the sealed test is repeated on actual NaMaster (or the scope is explicitly narrowed) and the abstract is brought into alignment with the documented threat-model limitations, the paper does not meet JORS standards.
