## CRITICAL ADJUDICATION 1 — Claude M1 (single-instance generality)

### The referee's claim
Abstract + §1 headline the reusable memory-bounded join/provenance/validation **machinery** as the *primary* deliverable, "designed to be re-run on any future frozen anomaly or coordinate list," yet the machinery is exercised exactly once, on the author's own list; no second input, no distinct catalog, no packaged/installable general tool — only pipeline-specific script paths. Substantiate generality (a second worked instance or a documented general interface) or soften the abstract/§1 framing to "a reproducible recovery pipeline for this list."

### (a) Does the paper CLAIM generality *beyond design intent*? — NO; it is explicitly hedged to design intent, and the design-level scoping the referee asks for is already present
The strongest generality wording is:
- **Abstract L51-55:** "The primary deliverable of this work is that reusable, memory-bounded join and provenance/validation machinery itself; the 181-row DESI DR1 catalog reported here is its **first instance**, produced by applying the machinery to **one** frozen historical input list."
- **§1 L130-134:** "…it is **designed to be** re-run on any future frozen anomaly or coordinate list. The 181-row DESI DR1 catalog reported below is **the first instance** produced by applying that framework to a single historical input list, **not the endpoint** of the contribution."

The paper does **not** claim generality is *evidenced* or *demonstrated*; it claims the machinery is *designed* to be reusable and is *demonstrated once*. That is exactly the design-level scoping the task names as "the minimal honest fix." It landed in the r9 machinery-first reframe (r9 audit cites abstract L44-48 / §1 L119-123) and is intact in r10. The referee's residual complaint is therefore a **venue/framing judgment** (is machinery-as-*primary*-deliverable, demonstrated once, an appropriate headline for an ApJS Catalog article?), not an undisclosed overclaim.

The one honesty gap not yet stated explicitly: the "reusable machinery" is realized only as this **DESI-specific** pipeline (see feasibility below), so "designed to be re-run on *any* future frozen anomaly or coordinate list" slightly overstates turn-key generality. A single optional clause acknowledging the DESI-specific instantiation would close that gap; it is framing-only, zero science impact.

### (b) Second-instance feasibility — INVESTIGATED against committed artifacts. A genuine independent second instance is NOT cleanly computable.
The committed builder (`scripts/build_desi_science_catalog_v320_r2.py`) is **hardwired to DESI DR1**:
- `load_desi_clusters` (L175) filters clusters on `survey_list` containing `desi_dr1`, joins to a DESI anomaly table by `desi_source_row`, and parses `desi_dr1_`-prefixed internal ids (L177, L187).
- `scan_fits` reads DESI-specific FITS columns `TARGETID`/`TARGET_RA`/`TARGET_DEC`/`DESI_TARGET`/`ZWARN`/`ZCAT_PRIMARY` (L71-88) and applies the DESI target-bit union mask `0x3000000000000007` (L291, tex L292) plus the `SURVEY==main` + `ZCAT_PRIMARY` + `ZWARN==0` zcatalog gates.
- There is **no committed non-DESI positional-join builder.** `sdss_native_rescore.py` etc. are BigAE **neural-net rescorers** (a `class BigAE(nn.Module)`, L77), not the join machinery.

Other frozen anomaly/coordinate lists **do exist** in the repo — `hf_staging/sdss_dr18_pathc_native.parquet` (77,905 rows), `gaia_dr3_anomalies.parquet` (500), `neowise_anomalies.parquet` (436), `erosita_dr1_anomalies.parquet` (298), `planck_cmb_anomalies.parquet` (200), and `apjs_submission_v3.1.161/pathc_multi_survey_matches.parquet` (637). **None can serve as a genuine second instance of this committed machinery without new code and new external data:**
1. The non-DESI lists carry survey-native schemas (e.g. SDSS `plate/mjd/fiberid/ra/dec/z/class/anomaly_score`; Gaia `source_id/ra/dec/...`) with **no** `survey_list`, `desi_source_row`, or `desi_dr1_`-prefixed tid — fed to the committed builder they filter to empty (`is_desi` mask) or KeyError.
2. Joining any of them against their **own** public catalog (SDSS specObj, Gaia DR3, …) to demonstrate cross-catalog generality would require (i) a new survey-specific join+gate module — the DESI target bitmasks and `ZCAT_PRIMARY`/`ZWARN` gates do not transfer — and (ii) downloading a new multi-GB public catalog that is not committed. That is a new mini-project, not a re-run.
3. `pathc_multi_survey_matches.parquet` shares the cluster schema (`cluster_id/n_detections/n_surveys/survey_list/ra_mean/dec_mean/best_score/member_ids/best_survey`) but is a **subset of the same BigBounce input** joined against the **same DESI catalog** → its DESI-containing rows would again be seed self-recovery of the same DESI members, **not an independent instance.**

**Second-instance feasibility verdict: NOT cleanly computable from committed artifacts.** A genuine independent second worked instance requires new survey-specific join code plus a new external public catalog; the committed machinery is DESI-hardwired, and the only cluster-schema list available is a subset of the same input against the same target catalog. Per the task's decision rule, the minimal honest fix is therefore **design-level scoping, not a second-instance run** — and that scoping is **already in the paper.**

### **VERDICT M1: DISCLOSED-RE-FLAG (single-instance/design-level scoping already landed) + SCOPE-VENUE-OPINION (machinery-as-primary-deliverable significance = DP3-16).** No required genuinely-new edit. One **optional, bounded, framing-only** honesty clause is available (note the machinery is realized as this DESI-specific pipeline; a different public catalog would need the analogous survey-specific gates) — GENUINELY-NEW-REAL(optional/minimal); zero science impact, zero fabrication.
